# FBA 包装数据维护助手 开发文档

适用组件：0.1.5。更新日期：2026-11-16。面向项目负责人及后续开发维护人员。

## 开发背景

本项目在亚马逊选品和领星 ERP 建料阶段，通常还没有实物样品可供核验。运营只能参考供应商资料、图片或经验填写销售包装数据，因此部分商品缺少 FBA 包装尺寸和重量，部分已有数值来自人工盲录。这些数值进入商品档案后，又会被后续业务继续引用。

当商品已经产生 FBA 业务，亚马逊费用预览报告中会提供用于费用估算的包装三边和重量。本助手利用这份现成报告，通过领星已有的 Listing 与本地商品配对关系，批量校正 ERP 商品资料，减少逐个查找、换算和录入的工作。

维护后的销售包装数据，可为后续发货计划的重量、尺寸引用及装箱、运费预估提供参考。商品包装方案或套装数量变化时，仍需采用与实际销售包装相符的新数据。插件只更新本地商品档案；已有发货计划、装箱任务和货件是否重新读取商品数据，应在相应单据中核对。

## 数据依据和适用边界

数据来源统一标记为“亚马逊费用预估”。它代表所导入报告中的数据，不能直接标记为“本次仓库实测”。报告日期、下载时间、插件导入时间和仓库测量时间是不同概念；标准费用预览字段不提供本助手可直接使用的测量时间，因此执行记录中的 `measurementDate` 保持为空。

亚马逊官方将费用预览定义为 FBA 库存的预计销售及履约费用报告，内容按报告机制更新，不能当作实时测量流。报告中的每一条重量、尺寸究竟源于申报、认证还是仓库复测，及其是否回写 Listing 编辑页，应另行取得对应后台证据。本助手不据此推断测量来源或测量日期。[Amazon 费用预览报告定义](https://developer-docs.amazon/sp-api/lang-en_EN/docs/report-type-values-fba#fba-fee-preview-report)

助手维护的是单件销售包装：包含包装的单品毛重和包装三边。它不能推算实装外箱、填充材料或托盘的最终尺寸、重量，也不代替出库时的整箱核验。

## 业务规则

| 规则 | 实现口径 |
| --- | --- |
| 匹配来源 | 所选店铺 + 报告 MSKU，读取领星已有 Listing 配对；运营无需维护对应表 |
| 身份核对 | ASIN 必须一致；报告有 FNSKU 时同时核对；继续核对本地商品 ID、SKU |
| 维护位置 | 本地商品档案的默认箱规，仅包装三边及单品毛重 |
| 默认模式 | 按报告更新，已有数值也参与差异计算；四项一致时不重复提交 |
| 仅补全 | 四项全部为空或 0 时处理，不按单个空字段零散补写 |
| 多来源 | 同一本地商品合并；不同来源数值冲突时，由操作者选一组完整数据，不取平均或最大值 |
| 其他站点 | 已识别为其他站点的报告行直接跳过，不查询其在当前店铺的配对；未知站点列待处理 |
| 净重和库存单位 | 不以库存计量单位为空或毛重小于既有净重拦截本次维护；净重保持原值 |
| 多箱规 | 必须能明确唯一默认箱规；多箱规商品先由操作者确认默认目标，不维护其他箱规 |

报告没有站点列时，助手无法仅凭该列判断归属，操作者仍需选对报告所属店铺。同一个本地商品可能被多个 Listing 共用，更新的是共享商品档案，不是给每个站点另存一套规格。

## 数据流和技术架构

处理顺序：原始报告 → 解析与换算 → 已有配对 → 商品现值 → 差异预览 → 人工确认 → 提交前复查 → 原生导入 → 商品读回核验。

| 阶段 | 主要模块 | 输入、输出与职责 |
| --- | --- | --- |
| 文件解析 | `parser.mjs`、`units.mjs`、`json.mjs` | 文本或工作簿转标准行，保留原始身份、数值、单位、行号和文件哈希 |
| 读取与配对 | `client.mjs`、`identity.mjs` | 通过领星当前会话读取店铺、Listing、本地商品；精确校验已有关系 |
| 差异计划 | `planner.mjs`、`app.mjs` | 合并本地商品、处理来源冲突、选择默认箱规、计算可更新及待处理状态 |
| 操作界面 | `ui.mjs`、`style.mjs`、`icons.mjs` | 紫色主题、真实商品主图、四项筛选、四列差异表、提交确认及结果记录 |
| 原生提交 | `native-context.mjs`、`native-import.mjs`、`workbook.mjs` | 生成最小 XLSX，限定原生业务和更新分组，单次交付文件 |
| 核验与恢复 | `execution.mjs`、`journal.mjs` | 提交前复查、浏览器内互斥、先存意图、提交后读回、保留未知结果 |
| 双渠道构建 | `scripts/bundle.mjs`、`scripts/build.mjs` | 同源生成 MV3 扩展、完整油猴、元信息及可重复 ZIP |

业务代码采用 JavaScript ES Modules；打包器将模块封装为浏览器脚本。SheetJS 固定在仓库内，构建时校验 SHA-256，不依赖运行时从外部加载解析器。测试使用 Node.js 22、Node 内置测试运行器，以及 jsdom、fake-indexeddb。

原生扩展采用 Manifest V3，匹配 `https://erp.lingxing.com/erp/*`，业务脚本在页面主执行环境工作，另有隔离环境的工具栏入口桥。油猴版本保持 `@grant none`，共用相同业务实现。实际挂载还需满足领星商品管理页面和原生上下文检查；重复注入只保留一个实例。

## 文件、单位和目标字段

支持 TXT、TSV、CSV、XLSX，单批最多 500 条报告数据、文件不超过 20 MB。文本兼容 UTF-8、带 BOM 的 UTF-16，以及匹配身份均为 ASCII 的 Windows-1252。旧编码中无法可靠还原的非 ASCII 身份不猜测；XLSX 中的 SKU、ASIN、FNSKU 必须保留文本身份。

| 报告字段 | ERP 维护字段 | 目标单位 |
| --- | --- | --- |
| `longest-side` | 包装规格长 | cm |
| `median-side` | 包装规格宽 | cm |
| `shortest-side` | 包装规格高 | cm |
| `item-package-weight`，兼容 `item-weight` | 单品毛重 | g |

三边按报告的最长、中间、最短边映射，不承诺商品摆放方向。数值以明确的十进制换算处理，长度保留 2 位、重量保留 4 位小数；界面同时保留报告原值与单位。

提交文件只包含“产品”工作表和七列：`*SKU`、`单品毛重`、`单品毛重单位`、`包装规格长`、`包装规格宽`、`包装规格高`、`包装规格单位`。SKU 为配对关系中的本地 SKU，以文本单元格写入。

领星原生更新分组严格限定为 `cg_product_gross_weight`、`cg_package`。商品净重、本体规格、外箱规格及成本不进入更新文件；读回时还会比较其他规格资料是否发生变化。

## 领星页面接入

| 用途 | 当前适配点 |
| --- | --- |
| 店铺及站点 | `/api/seller/getCountrySeller` |
| Listing 与配对 | `/listing-api/api/product/showOnline`，限定所选店铺和精确 MSKU |
| 本地商品详情 | `/api/product/info` |
| 原生导入 | `ProductManageSku` / `ImportFile`，业务 `001001002`，原生路径 `/ak-import-center/erp/import/001/excel` |

这些是已适配的页面内部能力，不是领星承诺稳定的公开 API。助手复用页面 `$get`、`$gwPost` 等请求层及已有登录会话，不额外索取 API 密钥，不记录 Cookie 或签名。原生组件、业务编号、导入类型或更新分组不符合预期时停止，不能临时扩大字段范围继续执行。

## 写入、核验和本地记录

操作者先核对差异并明确确认本批，提交前再次读取配对关系、目标箱规、旧数值、单位及其他规格快照，任一变化要求重新预览。程序通过 Web Locks 约束同一浏览器实例内同一公司的并行批次；该锁不能阻止其他设备修改商品。

上传前先将批次意图写入 IndexedDB。若持久化失败，不继续提交。上传文件只派发一次，随后读取原生任务状态和商品现值；四项数值、单位和受保护规格全部符合本批目标才记为成功。原生任务“已受理”本身不等于维护成功。

未能确认的行记为“结果待核实”，保留原生任务编号和已知状态，并阻止同一商品再次进入新批次。“重新核验”只读检查，不重新上传文件。暂停等待或刷新页面不会撤回已提交的原生任务。

执行记录按公司和账号哈希隔离，保存文件 SHA-256、报告日期、导入时间、来源行及原始值、采用来源、目标商品与箱规、旧值、新值、任务编号及结果。记录存于当前浏览器的 IndexedDB；清理领星站点数据会删除本机记录。它是来源追踪和异常恢复依据，不是云端统一审计库。

## 自动更新与发布

从 0.1.5 起，完整油猴与元信息共用 `userscriptMetadata()` 生成，保持原脚本名称和 namespace。Tampermonkey 按 `@version` 判断版本，使用 `@updateURL` 检查元信息，再从 `@downloadURL` 获取完整程序。[Tampermonkey 官方说明](https://www.tampermonkey.net/documentation.php?locale=en&q=update_url)

| 文件 | 固定地址与职责 |
| --- | --- |
| 更新元信息 | main 下的 `scripts/lingxing-package-data-assistant/lingxing-package-data-assistant.meta.js`；只包含元数据注释 |
| 安装与更新程序 | main 下同目录的 `lingxing-package-data-assistant.user.js`；完整程序及固定解析器 |
| 版本归档 | `lingxing-package-data-assistant-v版本号` 的 Git tag 和 Release；发布后不移动、不替换同版本资产 |

main 的 user/meta 是已安装用户的更新通道。开发分支不作为运营更新源，每次必须递增版本、同次提交两项生成文件，通过测试和独立评审后再合并。程序没有新增 `@require` 或远程运行时依赖。

0.1.4 及更早版本未配置本次更新地址，需要先覆盖升级一次。后续更新是否自动安装取决于 Tampermonkey 的更新设置与 GitHub 网络连通，更新完成后刷新领星页面生效。自动更新程序不等于自动导入报告或自动修改 ERP。原生扩展继续手动升级。

## 开发、验证和维护入口

权威源码：[GitHub 组件目录](https://github.com/wrangler1024/crossborder-userscripts/tree/main/extensions/lingxing-package-data-assistant)。`src/`、`extension/`、`scripts/` 和固定 vendor 是维护入口；不要直接编辑生成油猴或 `dist/`。

在组件目录使用 Node.js 22：

```bash
npm ci --ignore-scripts
npm test
npm run build
npm run check:generated
git diff --exit-code -- ../../scripts/lingxing-package-data-assistant/
```

验证已提交候选时，先运行测试再构建，以免生成步骤掩盖未提交或过期的 user/meta。测试覆盖解析换算、身份精确匹配、来源冲突、默认箱规、最小更新文件、提交前变化、持久化失败、账号隔离、未知结果及更新元信息。发布需在干净提交重建并核对 ZIP 内容、版本、哈希、CI、独立评审和远端实际下载。

现有用户反馈已确认原生试用包实际回填后 ERP 保存的尺寸、重量正确；未记录具体条数、操作者角色或原生任务号，不能扩大为所有角色和渠道均已验收。油猴运行适配、普通运营角色及长期自动更新行为仍应在使用环境分别留证。当前自动更新改造不改变 ERP 写入逻辑。

后续领星页面升级优先检查原生组件与请求结构，报告导出变化优先检查表头、身份类型和单位。错误定位及真实业务证据留在私有项目材料，不进入公开源码、测试或 Release。
