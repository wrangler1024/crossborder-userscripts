# 发货异常判定调整(揽收负值去异常化)

- 日期:2026-09-15
- 决策人:Jeff
- 版本:v0.1.13(`version_name: 0.1.13-shipping-anomaly`)
- 性质:业务口径变更,影响异常判定、面板告警、明细标记、CSV 判定列与异常导出

## 一、口径变更

| 项 | 旧口径(v0.1.12 及以前) | 新口径(v0.1.13) |
|---|---|---|
| 揽收时效 < 0(物流商实际接手早于发货登记) | 判为「揽收异常」导出 | **正常现象**,不计异常;负值保留展示,拆解表仅提示「含 N 单负值」 |
| 上网时间早于下单时间 | 无监控 | **判为「发货异常」**(重大业务事故),页顶红色告警 + 独立导出 |

背景:揽收早于发货登记只是仓库发货登记滞后,属正常运营现象;而物流轨迹的上网点早于买家下单时间,意味着包裹(或运单号)先于订单存在,涉嫌虚假发货/运单复用/错发错绑,是必须特别关注的重大业务事故。

## 二、判定实现

```js
isShippingAnomaly(order) =
    Number.isFinite(order.onlineMs)
 && Number.isFinite(order.orderMs)
 && order.onlineMs < order.orderMs;   // 严格早于;相等不算;缺失不算
```

- 上网时间来源不变:接口 `onlineTime` 优先,缺失取轨迹最早有效时间(来源标记「轨迹起始时间补取」);
- 揽收负值与发货异常相互独立:一单可同时「揽收为负」且「非发货异常」。

## 三、界面与导出变化

1. 页顶新增红色告警条:`⚠ 发货异常 N 单:上网时间早于下单时间(重大业务事故)`,仅 N>0 时显示;
2. 页脚导出按钮更名:`导出揽收异常(N)` → `导出发货异常(N)`,导出当前已确认筛选范围内全部发货异常明细(不受 10 单预览限制,无异常禁用);
3. 明细预览:异常单订单号下红色标记「发货异常」;
4. CSV:末尾「揽收判定」列更名「发货判定」,值为 `发货异常(上网早于下单)` / `正常` / `无法判定`(上网或下单缺失);「上网时间来源」列保留;
5. 拆解表揽收行负值提示改为「含 N 单负值(非异常)」。

## 四、真机验证(20260915,已签收全量 14933 单)

- 发货异常:**8 单**(样例:XMWU39A68023,下单 09-07 12:44,上网 09-03 12:00,早于下单 96.7h,上网来源=轨迹补取;其余 4 单抽样早于下单 8.7h–35.9h);
- 揽收负值:173 单,按新口径不再计异常;
- 上网来源分布:绝大多数为「接口上网时间」,少数为「轨迹起始时间补取」。

## 五、测试

`tests/core.test.js` 23 项全绿,其中异常用例重写为:
- 上网早于下单 → 唯一命中;
- 上网等于下单 → 不算;缺失 → 不算;
- **揽收负值但上网晚于下单 → 不算**(口径回归防护);
- CSV 断言「发货判定/发货异常」,且不再出现「揽收判定」。
